# KuaiRand 双塔召回项目：三人并行开发、五周集成计划

> 文档性质：待实施计划。本文不代表代码已实现、数据已处理或实验已完成。
> 开发方式：三人使用 Codex 辅助开发；每周合并一个可运行系统，并生成统一的 Stage Performance Report。

## 1．项目目标、资源与责任边界

五周内交付统一链路：

**全量日志处理 → 双塔训练 → 视频向量生成 → ANN 检索 → 统一评估 → 本地请求演示 → 中英作品集页面。**

业务任务：在用户发起请求时，利用此前已产生的观看反馈，从当时符合资格的视频库中召回 100 个可能产生长观看的视频。以官方 `long_view=1` 为正反馈；离线指标不解释为线上 CTR、留存或收入提升。

### 资源与排期假设

- 每人有 Colab Pro 和 A100 使用条件，每个 session 至少 50 GB 临时磁盘。
- 团队另有至少 200 GB 可用的私有共享 Google Drive；不把 Colab 临时磁盘视为持久存储。
- Codex 负责辅助代码编写；成员负责检查接口、运行 Colab、审查结果和解释实验。
- 五周按功能和验收里程碑安排，不按纯手写代码工时估算；训练时间由第二周的实测吞吐决定。
- 三个 Colab 运行独立作业，不搭跨 session 分布式训练。
- 原始数据、checkpoint、完整向量和索引保存在私有存储。Git 只保存代码、配置、测试、文档与轻量聚合结果。

### 不重复的模块分工

| 成员 | 唯一负责模块 | 个人实验 | 公共模块使用规则 |
|---|---|---|---|
| **Ziqi** | 下载、清洗、分片、历史索引、物品塔 | ID 与类别／时长特征的差异 | 使用 Yutao 的训练器和 Ricky 的评估器 |
| **Yutao** | 用户塔、损失函数、训练器、恢复训练、统一 CLI | 无历史、平均池化、时间衰减池化 | 使用 Ziqi 发布的数据与物品塔 |
| **Ricky** | 候选资格、评估器、索引、请求入口、网站集成 | 精确检索与 ANN 的效果／成本 | 使用公共模型和训练器，不维护第二套训练流程 |

第一天共同冻结最小接口、数据字段和合成测试样本。三人从第一周同时开发，通过接口测试解耦，不等待某位成员完成整个模块。每周的主成果是合并系统的性能，个人实验是补充证据。

## 2．共同技术方案与接口

本节中的目录、字段和命令都是拟实施规范，并不表示文件已经创建。三人确认本计划后，再按周建立对应代码。

### 2.1 数据与持久存储

研究代码拟集中于 `research/kuairand/`。共享 Drive 采用以下布局：

```text
kuairand/
├── raw/27k/                  # 官方压缩包，只获取一次
├── datasets/v1/              # 不可变分片、历史索引、特征与 manifest
├── runs/<owner>/<run_id>/    # 每人的独立实验、checkpoint 与日志
└── releases/<stage>/         # 冻结模型、向量、索引与阶段报告
```

实现步骤：

1. 一次性获取官方 27K 压缩包，核验官方校验值并记录 SHA-256。
2. 顺序读取压缩包中的 CSV，分块转换；不同时保留完整解压数据和处理产物。
3. 将事件按用户分区组织，生成 Parquet 分片、紧凑历史索引和视频特征分区。
4. 分片上传校验成功后释放临时文件；所有分片完成后才发布正式 manifest。
5. manifest 记录来源、校验值、行数、时间边界、过滤原因、用户子集和特征版本。
6. 正式训练把当前与下一分片预取至 `/content`；数据缓存上限初设 16 GB，根据剩余磁盘空间缩减。
7. 历史和视频特征采用分区加载或有界缓存，避免训练时逐样本访问挂载 Drive。

Parquet 分片以 256–512 MB 为初始目标，第二周依据读取吞吐调整。数据版本由 Ziqi 发布，其他人只读；每个人仅向自己的实验目录写入。

新 session 的入口：

```text
挂载共享 Drive → 检出固定代码版本 → 读取 manifest
→ 加载当前所需分片 → 恢复 checkpoint → 继续运行
```

挂载后可以直接访问持久数据，不需要重新从官网获取或重新预处理；新 session 的本地高速缓存仍需重新填充。50 GB 临时磁盘的初始预算为：数据缓存 16 GB、模型与保存缓冲 8 GB、向量／索引缓冲 10 GB、依赖与安全余量 16 GB。完整索引和中间处理的峰值空间需实测；空间不足时缩小工作分片，不静默突破预算。

### 2.2 标签、切分与泄漏控制

| 时间区间，按数据记录日期 | 用途 |
|---|---|
| 4 月 8–14 日 | 历史预热 |
| 4 月 15–28 日 | 训练 |
| 4 月 29 日–5 月 3 日 | 验证、选模型与每周阶段评估 |
| 5 月 4–8 日 | 最终测试，仅第五周冻结模型后使用 |

- 实施前核验时间戳与日期字段的时区对应关系，核验后冻结配置。
- 主训练使用常规日志；随机曝光单独保留为诊断集，不混入主指标。
- 历史只包含请求前已产生的反馈；播放结果采用经过核验的完成时间规则。
- 仅删除可以确认的重复记录，保留真实重复观看。
- 排除跨月统计表、时间来源不明的动态画像和未来反馈；训练词表及归一化参数仅由训练期决定。
- 视频资格按已知发布时间保守构建；日期只有天粒度时，从次日开始纳入。缺失时间资格单独统计。
- 主协议允许重复观看，不默认排除历史看过的视频。
- 保留冷启动目标和缺失特征样本；不能因模型不支持而静默删除验证／测试目标。
- 历史候选资格无法完整还原下架、可见性变化及内容修改，报告必须说明该限制。

### 2.3 模型方案

- **物品塔：**固定哈希视频 ID Embedding，可选类别 Embedding 和时长特征；小型 MLP 输出 64 维向量。
- **用户塔：**用户 ID、场景和请求时间上下文，可选最近 50 次正反馈历史的平均或时间衰减池化；输出 64 维向量。
- 两塔输出归一化，使用点积匹配。
- 使用批内负样本，屏蔽重复目标；潜在假负样本限制在报告中披露。
- 先实现分块精确 Top-K，再实现 IVF-PQ 压缩索引。
- 首期不加入文本大模型微调、精排、多任务学习或多兴趣网络。

### 2.4 公共接口与运行入口

| 接口 | 输入与输出约定 | 负责人 |
|---|---|---|
| 数据批次 | 用户、目标视频、请求时间、场景、视频特征、历史引用／mask | Ziqi |
| `encode_items(item_features)` | 返回 `[N, 64]` 物品向量 | Ziqi |
| `encode_users(user_features, history, mask)` | 返回 `[B, 64]` 用户向量 | Yutao |
| `train(config, manifest, resume)` | 返回可恢复 checkpoint 和训练记录 | Yutao |
| `retrieve(user_vectors, snapshot, k)` | 返回视频 ID、分数和版本信息 | Ricky |
| `evaluate(predictions, evaluation_bundle)` | 返回统一效果指标和覆盖统计 | Ricky |

统一 CLI 拟提供 `prepare / train / export / index / evaluate / stage-report`，并提供校验、模型冻结和本地请求演示入口。Yutao 维护入口；各命令的业务实现由对应负责人提供。

checkpoint 保存模型、优化器、混合精度状态、随机数状态、轮次、分片和批次游标。先完成文件上传及校验，再发布完成标记；恢复只选择完整 checkpoint。定期清理较旧的大型 checkpoint，保留必要审计记录和冻结模型，避免占满 Drive。

每个模型、向量和索引绑定数据、特征、配置与代码版本。Colab Notebook 只负责初始化、选择配置、启动脚本和展示结果。新增训练依赖隔离在专用环境。

### 2.6 第一天冻结的字段契约

**原始数据到标准事件：**

| 字段 | 类型／含义 | 使用限制 |
|---|---|---|
| `request_id` | 稳定且唯一的事件标识 | 重跑和抽样结果可对齐 |
| `user_id` / `item_id` | 原始版本内匿名整数 ID | 不能混用不同官方版本的 ID |
| `time_ms` | 请求时间，毫秒 | 用于时间切分和历史边界 |
| `available_ms` | 反馈可用时间，毫秒 | 只在可验证时写入，不把缺失当作即时反馈 |
| `tab` | 场景 ID | 不把不同界面的点击含义混为一谈 |
| `long_view` | 官方二值长观看标签 | 本项目主训练正反馈 |
| `is_random` | 随机曝光标记 | 主训练和诊断分开 |
| `split` | warmup／train／validation／test／random | 由唯一的数据流水线生成 |

**标准数据到训练批次：**

- 用户字段：`user_id[B]`、`time_ms[B]`、`tab[B]`。
- 目标字段：`item_id[B]`、`category[B]`、`duration[B]`。
- 历史字段：ID、类别、时长、反馈年龄，各为 `[B,L]`；有效位置 mask 为 `[B,L]`。
- `L` 默认 50；空历史使用全 false mask，不能产生 NaN。
- 缺失类别、时长使用明确缺失标记；时长单位统一为秒，不能在不同模块混用毫秒。
- 历史条目由 Ziqi 的批次组装器负责取得；Yutao 的模型不得自己查询未来日志。
- 主训练使用所有合格正样本，确定性地混合多个用户形成 batch；避免按单个用户顺序组成批内负样本。
- 顺序、混合规则及 seed 固定，恢复游标必须能还原下一批次，不以“差不多读过”为覆盖证据。

**训练到导出与检索：**

- 原始视频 ID 与向量逐条对齐，分片内按 ID 排序。
- 向量统一为 64 维；分片记录行数、ID 范围、文件校验值、数据和模型版本。
- 导出分区使用半开区间 `[start_id,end_id)`，三人同时编码时分区不可重叠。
- 合并导出时核验完整候选清单，不能仅比较三个分区的总行数。
- 索引返回的内部编号由 Ricky 映射回原始视频 ID，不由前端推测。

### 2.7 预设实验矩阵与选择规则

| 配置 | 用户塔 | 物品塔 | 主要解释的问题 |
|---|---|---|---|
| `baseline` | ID＋上下文，无历史 | 视频哈希 ID | 最小神经召回基线 |
| `user-history` | ID＋上下文＋平均历史 | 视频哈希 ID | 历史带来的增益 |
| `item-content` | ID＋上下文，无历史 | ID＋类别＋时长 | 物品特征带来的增益 |
| `combined` | ID＋上下文＋平均历史 | ID＋类别＋时长 | 两侧增益能否共同成立 |
| `time-decay` | ID＋上下文＋衰减历史 | ID＋类别＋时长 | 兴趣时效性的增益 |

热门基线统一使用训练窗口的正反馈计数和同一候选资格协议。第一版不引入独立的实时热度服务，报告明确它是冻结训练期热门基线。

第二周四组配置使用相同数据、seed、输出维度、训练预算和评估包。第三周只对平均／衰减历史进行有限比较，不同时搜索多种网络深度和多个维度。

主模型按验证 Recall@100 选择；非常接近时优先候选覆盖更稳定、成本更低的配置，并同时报告 NDCG@100。索引参数用验证集选择。最终测试不得参与这些决策。

全量首轮固定为一次完整训练样本遍历，后续增加轮数必须由验证结果和预算支持，不预先承诺多轮全量调参。稳定性复跑属于同配置新 seed 的独立 run，不覆盖原实验。

## 3．五周逐人任务与每周合并验收

### 第 1 周：Stage 1 — 最小完整系统

**Ziqi：数据和基础物品塔**

1. 实现官方获取、校验、顺序压缩包读取和分块转换。
2. 准备约 100 用户、覆盖全部时间窗口的真实开发样本。
3. 实现视频特征查询和基础 ID 物品塔。
4. 启动 27K 全量转换，发布已完成分片清单。
5. 添加缺失字段、精确重复和时间切分检查。

**Yutao：基础用户塔和训练系统**

1. 建立配置、统一 CLI 和训练循环。
2. 实现用户 ID＋上下文的基础用户塔。
3. 接入物品塔，实现归一化点积、批内损失和重复目标屏蔽。
4. 实现 checkpoint 保存／恢复，包括优化器、随机状态和数据游标。
5. 提供 Colab 初始化入口；先接合成样本，再接真实开发样本。

**Ricky：基础评估和精确检索**

1. 实现训练期热门基线、统一 Recall@100 和 NDCG@100。
2. 实现分块精确 Top-K，检查候选资格和 ID 映射。
3. 建立固定小规模验证请求集。
4. 建立阶段报告格式、集成检查和指标导出。
5. 用手算小样本验证指标、资格过滤和排序。

**本周合并步骤与验收**

先合并数据和模型接口，再接训练器与评估器。合并版本运行：

`小样本 → 训练 → 导出向量 → 精确检索 → Stage 1 报告`

报告包含热门基线、基础双塔、数据规模、训练吞吐和来源。合成数据只作为正确性验证，真实小样本也不解释为业务收益。

**交接产物**

| 提供者 → 接收者 | 本周交接 | 接收者如何验收 |
|---|---|---|
| Ziqi → Yutao | 小样本 manifest、批次读取器、物品塔 | 不改数据即可完成一个训练批次 |
| Yutao → Ricky | 模型配置、完整 checkpoint、向量导出接口 | 能生成对应视频向量并核验维度 |
| Ricky → 全员 | 评估器、报告 schema、手算测试 | 三人调用同一个指标入口，结果一致 |

**必须通过：**新环境可启动、小样本可端到端运行、训练中断可恢复、未知与空历史不崩溃。全量转换尚未完成不阻塞本周的小样本集成。

### 第 2 周：Stage 2 — 行为历史与物品特征合并

**Ziqi：历史构造和物品侧增强**

1. 完成 27K 标准化数据及 manifest。
2. 实现历史索引和按批次组装，避免给每条请求重复保存展开历史。
3. 实现类别／时长增强物品塔和未知特征处理。
4. 从 27K 内生成固定约 1K、5K 用户递增子集；不拼接不同官方版本的重编码 ID。
5. 通过公共训练器运行物品特征消融。

**Yutao：行为用户塔和训练效率**

1. 实现带 padding mask 的平均池化用户塔。
2. 接入基础／增强物品塔和历史配置。
3. 加入混合精度、分片预取、数据等待和训练吞吐统计。
4. 测量 batch size 对显存和吞吐的影响，冻结后续默认值。
5. 运行无历史／有历史消融。

**Ricky：冻结比较协议和联合评估**

1. 冻结跨周参考请求和候选集合，保存校验值。
2. 实现长尾、冷启动、候选资格覆盖切片。
3. 核验精确索引与分块矩阵检索结果一致。
4. 加入导出耗时、索引成本及峰值内存统计。
5. 使用合并代码评估四组配置：基础、仅增强用户、仅增强物品、两侧同时增强。

**本周合并步骤与验收**

共同训练器接入两侧增强后，冻结集成 commit，从同一评估包运行四组配置。生成 Stage 2 报告，同时展示固定参考集和当前规模结果。第二周用实测吞吐估算全量遍历时间，决定第三周的训练预算。

**交接产物**

| 提供者 → 接收者 | 本周交接 | 接收者如何验收 |
|---|---|---|
| Ziqi → Yutao | 带 mask／年龄的历史批次、两个物品塔模式 | 无需改变训练器即可切换配置 |
| Yutao → Ricky | 四个配置的 run manifest 和 checkpoint | 同一评估包全部可运行，无私有预测格式 |
| Ricky → 全员 | 固定参考包、分组规则、四组总表 | 能区分联合收益、单侧收益及覆盖变化 |

**必须通过：**没有未来历史、四组采用一致训练预算、每个配置都能完整导出和评估。候选库和请求样本的 hash 必须写入报告。

### 第 3 周：Stage 3 — 全量训练与 ANN 链路

**Ziqi：全量数据审计和编码输入**

1. 核对全量行数、过滤原因、训练正样本数、缺失和时间资格。
2. 验证历史跨分片连续，测量视频特征查询和缓存成本。

4. 提供完整候选库的分片编码输入。
5. 生成数据分布和长尾图表。

**Yutao：用户侧定型和全量遍历**

1. 实现时间衰减池化，与平均池化做有限比较。
2. 根据验证结果冻结主训练配置。
3. 启动全部用户、全部合格训练正样本的一次完整遍历。
4. 记录分片消费、样本数量和恢复次数；中断后继续同一 run。
5. 检查恢复没有造成系统性漏读或重复消费。

**Ricky：ANN 和本地请求入口**

1. 实现 IVF-PQ 压缩索引及批量检索。
2. 用精确 Top-K 参考结果选择索引参数。
3. 实现资格过滤、结果去重和不足 K 的明确处理。

5. 提供本地推荐入口，返回候选和模型／索引版本。

**本周合并步骤与验收**

运行：

`恢复训练 → 分片导出 → ANN 索引 → 请求召回 → Stage 3 报告`

目标为完成一次全量遍历。未完成时记录真实覆盖比例、剩余分片和预计耗时；第四周优先续训，减少新增实验。全用户采样训练不能标为全量训练。

**交接产物**

| 提供者 → 接收者 | 本周交接 | 接收者如何验收 |

| Ziqi → 全员 | 全量质量报告、候选清单、特征版本 | 原始／清洗／过滤统计可对账 |
| Yutao → Ricky | 主模型 checkpoint、样本消费记录 | 实际消费数与目标训练数一致或明确标为部分 |

**必须通过：**分片恢复不漏不重、压缩索引可加载、模型与索引版本一致、ANN 保真度可测。全量训练耗时超过周预算时保留正确性与进度，第四周继续同一个 run。

| Yutao → Ricky | 冻结模型、导出工具、恢复说明 | 新 session 能还原相同模型和分数 |
| Ricky → 全员 | 完整索引、验证报告、页面预览 | 可以演示请求；页面数值全部来自产物 |

**必须通过：**向量 ID 对账、资格过滤、未知用户兜底、归一化分数一致、页面中英事实一致。若效果不足，保留真实结果，不能手填更好指标。

## 4．每周合并机制与 Stage Performance

### 4.1 每周固定节奏

- **周初：**共同确认接口、三个独立任务清单和验收命令。
- **周中：**持续合并可运行的小 PR，避免周末一次性拼接。
- **周末前：**冻结阶段集成 commit，未完成的个人实验留在实验分支。
- **周末：**从该 commit 运行统一阶段命令，生成不可覆盖的报告，共同解释变化。

遵循仓库已有的 Issue、`feature/<issue>-<name>` 分支和交叉审查流程。

协调人按周轮换：**Ziqi → Yutao → Ricky → Ziqi → Yutao**。协调人负责集成和验收，不替其他人完成模块。交叉审查为 Ziqi 审 Yutao、Yutao 审 Ricky、Ricky 审 Ziqi。

### 4.2 Codex 任务约定

每个任务明确以下内容：

1. 所属模块和允许修改的文件范围。
2. 输入、输出和公共接口版本。
3. 需要调用的公共模块，禁止另写的重复逻辑。
4. 可执行验收命令和预期产物。
5. 本次结果的证据边界与未完成事项。

共享配置与依赖变更单独提交 PR。三个人的实验目录互不覆盖；每周合并后重新运行总系统，个人本地结果不能替代阶段验收。

**可直接交给 Codex 的任务卡格式：**

```text
任务：W<周数>-<成员>-<模块>
目标：本任务解决的具体问题。
允许修改：明确文件／模块；公共接口变更需单独提出。
已冻结输入：数据版本、配置、字段契约。
实现步骤：按本周任务编号执行。
交付产物：代码、测试、说明，以及实际生成结果的位置。
验收：可运行命令＋必须成立的不变量。
禁止重复：调用公共训练器／评估器，不另建同功能实现。
证据：记录 commit、数据 hash、配置 hash、运行环境。
```

第一周中间模块尚未合并时，各自使用共同合成样本验证接口；真实数据就绪后替换输入，不修改接口。公共训练器、评估器或 manifest 发生变化时，三人共同审查，不能仅在个人实验中绕过。

### 4.3 阶段报告生成步骤

1. 协调人确认三个模块 PR 已合并，记录唯一集成 commit。
2. 每个参与比较的模型从该 commit 和同一数据版本运行，保存各自 run manifest。
3. Ricky 的公共评估器读取候选／请求协议，验证比较条件一致。
4. 生成固定参考报告和当前规模报告；未测量字段明确为 `null`。
5. 报告生成器汇总实验，写入新的只读阶段目录，不覆盖上一周报告。
6. 三人检查结论与证据对应，记录通过／未通过项以及下一周调整。

阶段发布目录拟包含 `release_manifest.json`、`stage_report.json`、`stage_report.md` 和聚合图表。只读阶段产物绑定实际运行的 commit，不绑定事后更新的分支 HEAD。

### 4.4 每份报告的必填内容

| 类别 | 内容 |
|---|---|
| 版本 | commit、配置 hash、数据、特征、模型和索引版本 |
| 数据覆盖 | 用户、训练正样本、已消费样本、候选视频数量 |
| 模型效果 | Recall@100、NDCG@100、热门基线、长尾／冷启动切片、候选覆盖 |
| 检索质量 | ANN Top-100 对精确 Top-100 的重合率 |
| 性能 | 训练吞吐、数据等待、导出／索引耗时、P50／P95 延迟、峰值内存 |
| 可靠性 | 恢复检查、版本一致性、遗漏／重复计数 |
| 阶段结论 | 相对上一阶段变化、成本和待解决问题 |

单目标请求下 Recall@100 等价于 HitRate@100。没有进入候选库的正目标既要计入覆盖统计，也要在端到端指标中计为未召回。

第二周冻结参考评估包，后续保留固定参考结果和当前规模结果。只有请求、候选协议相同的结果才能直接比较；候选规模改变不能写成模型提升。

性能测量固定硬件、batch size、并发、预热和请求样本，明确延迟是否包含特征读取和用户塔。CPU 与 GPU 分开报告。ANN 重合率 95% 是初始调优目标，不是预先承诺的结果。

### 4.5 全量覆盖的四项证据

| 覆盖维度 | 验收证据 |
|---|---|
| 全量数据处理 | 原始行数、处理行数、过滤原因可以对账 |
| 全量训练 | 所有合格训练分片至少完成一次消费，样本数可核对 |
| 全量物品编码 | 目标候选 ID 与向量 ID 一致，无遗漏和重复 |
| 全候选评估 | 抽样请求对完整合格候选库评估，明确披露请求样本量 |

不要求对全部历史请求执行精确全库检索。使用固定代表性请求样本、完整候选库和分块精确参考结果，分别验证推荐效果与 ANN 误差。

### 4.6 数据规模阶梯与跨周比较

| 阶段 | 训练用户范围 | 候选范围 | 作用 |
|---|---|---|---|
| 第一周开发样本 | 27K 内约 100 用户 | 明确记录的小候选库 | 正确性和接口验证 |
| 第二周参考规模 | 固定约 1K 用户 | 冻结参考候选集合 | 后续跨周回归 |
| 第二／三周中规模 | 固定约 5K 用户 | 当前规模候选库 | 选择模型、估算扩展成本 |
| 第三／四周正式规模 | 全部合格用户 | 完整合格候选库 | 全量训练与检索 |
| 第五周测试 | 冻结测试请求样本 | 完整合格候选库 | 一次最终评估 |

递增用户子集采用固定 seed 的稳定用户排序，记录实际 ID 清单及 hash；较小子集包含于较大子集，不临时挑选表现好的用户。参考请求按固定 seed 的稳定事件抽样选取；大规模精确检索可以使用更少请求，但必须报告不同样本量。

冷启动定义为目标视频在训练期没有合格正反馈；长尾初始定义为训练正反馈数 1–5。定义在第二周冻结，报告每组请求数，空切片使用 `null`，不把空组表示为零效果。

### 4.7 常见阻塞的处理方式

| 阻塞 | 立即处理 | 谁继续独立推进 |
|---|---|---|
| 全量转换未完成 | 保持正式数据版本未发布，使用已验证小样本 | Yutao 开发模型；Ricky 开发检索和评估 |
| Drive 读取慢 | 先测等待占比，扩大顺序读取、调整分片和本地缓存 | 三人仍使用同一 manifest，不另做清洗 |
| session 中断 | 仅恢复已校验 checkpoint；未确认输出不发布 | 其他独立 run 不受影响 |
| 全量训练超过预算 | 延续同一 run，减少额外实验，记录部分覆盖 | Ziqi 完成数据审计；Ricky 继续已有模型索引验证 |
| 模型改进未提升 | 保留基线及消融，解释有效范围和成本 | 正常完成系统与页面，不扩大无界调参 |
| 合并冲突／接口变化 | 由模块负责人修复并运行集成测试 | 未涉及该接口的任务继续 |
| 存储不足 | 清理可重建缓存和旧 checkpoint，缩小输出缓冲 | 保留数据版本、审计记录和冻结产物 |

若共享 Drive 在三人并行下持续无法满足读写需求，单独讨论迁移对象存储的预算；该变化不属于自动执行的既定范围。

## 5．测试、完成标准与范围边界

必须覆盖：

- 时间切分、历史反馈可用时间、未来统计泄漏。
- 未知用户／物品、空历史、缺失类别、真实重复观看。
- 批内重复目标屏蔽、padding mask、向量维度和归一化。
- 手算精确检索、候选时间资格、ANN 去重与不足 K。
- 小样本连续训练和恢复训练在预定容差内一致，消费数量可核对。
- checkpoint、模型、特征、数据和索引版本混用时明确失败。
- 原始数据与大文件不进入 Git，页面只读取脚本生成的聚合指标。
- 新研究代码测试，以及现有 Python、JavaScript、类型检查和网站构建通过。

完成标准为：**系统可复现、覆盖可证明、每周合并可追溯、结果真实且可解释。** 双塔是否胜过热门基线属于实验结论，不作为项目完成的硬条件。

五周内不扩展精排、文本大模型微调、跨 Colab 分布式训练、在线 A/B 或生产云部署。项目验证真实日志上的召回方法与工程链路，不声称已在快手生产环境实施或获得线上业务收益。
